## Findings (2026-10-20, researched directly)

### B. Grok Bot (consumer product, docs.x.ai/grok-bot)

**CONFIRMED:**

- **Remote MCP client support: YES.** Grok (the consumer product) supports
  adding custom MCP connectors over the public internet, with Grok's
  servers discovering and calling tools your MCP server exposes.
  Source: docs.x.ai/grok/connectors (fetched 2026-10-20). A dedicated
  tunneling guide (docs.x.ai/grok/connectors/custom-mcp-tunneling) confirms
  **Streamable HTTP transport works** (it explicitly warns the older SSE
  transport doesn't work with one tunneling option, but Streamable HTTP
  does) — matches the source spec's own transport choice (section 11.11),
  no mismatch.
- **Static bearer-token auth: YES, confirmed directly.** The developer CLI
  docs (docs.x.ai/build/features/mcp-servers) explicitly show: `grok mcp
  add --transport http api https://mcp.example.com/mcp --header
  "Authorization: Bearer ${API_TOKEN}"` — a static header, no interactive
  OAuth required. A third-party real-world example (poster.ly's setup
  guide) independently confirms the same pattern for the actual consumer
  Grok Bot Settings > Plugins > custom connector flow: paste a hosted MCP
  endpoint URL with a bearer token, no OAuth dance. **This directly
  resolves the source spec's open question 18.1 (whether MCP OAuth needs
  to be pulled forward) — answer: no, static bearer auth works today, OAuth
  can stay deferred as the spec already assumed.**
- **Connector timeout: three minutes, confirmed from the official Grok Bot
  changelog** (x.ai/changelog/bot, fetched 2026-10-20): "A connector that
  stops responding times out after three minutes, so your Bot can carry
  on." **This is the single most important finding** — the source spec's
  40-second long-poll design (`sit`/`play` holding the connection open
  waiting for an opponent) is comfortably inside this limit, with roughly
  4.5x headroom. The 40-second design as written is safe against this
  confirmed ceiling.
- Bots run on a persistent cloud computer and **continue working when the
  user's device is closed** (confirmed, docs.x.ai/grok-bot/overview) —
  relevant to the spec's scheduled "Open Play" convention.

**NOT CONFIRMED / NEEDS FURTHER CHECK:**

- No documented hard ceiling found on *maximum tool calls per run* or
  *maximum single continuous run/turn duration* for Grok Bot specifically
  (distinct from the three-minute per-connector-call timeout above, which
  is about one stalled call, not total run length). Usage resets weekly
  per plan tier (confirmed) but that's a billing/usage cap, not a
  technical per-turn limit. Not found, not assumed — flagged as open.

### A. OpenClaw (this runtime)

**CONFIRMED, from this system's own tool specifications (direct evidence,
not inference from unrelated docs):**

- The `process` tool's own poll action is explicitly capped: "wait up to
  30000 ms before returning; higher values are clamped to 30000." This is
  real, documented evidence that **a single long-poll-style wait within
  one tool call in this runtime is bounded at 30 seconds**, not 40.
- The `exec` tool supports a `yieldMs` parameter (default 10000ms) before
  automatically backgrounding a long-running command, plus explicit
  background/foreground continuation via `process` actions — i.e. the
  *pattern* for a long-running wait in OpenClaw is background-and-poll,
  not a single call blocking past ~30s.
- **Direct architectural implication for the source spec's design:** if a
  BOTTAGON reference bot or the implementing agent itself runs as an
  OpenClaw agent calling the BOTTAGON HTTP/MCP API directly, a single tool
  call should **not** be built to block for the full 40 seconds the spec
  assumes — 30s is the safer, confirmed ceiling for a single blocking call
  in this runtime, and the background/poll pattern already used by
  `exec`/`process` is the correct native idiom to mirror if an OpenClaw
  agent is a BOTTAGON contestant.

**NOT CONFIRMED / NEEDS OWNER DECISION:**

- No single documented "maximum tool calls per run" ceiling found for
  OpenClaw subagent/session turns in the material checked so far — this is
  governed by run-timeout/budget configuration (e.g. `sessions_spawn`'s
  `runTimeoutSeconds`), which is a configurable policy, not a fixed
  platform constant. Needs an explicit decision (what timeout to configure
  for a BOTTAGON reference-bot subagent), not a "platform limit" to
  discover.
- Whether OpenClaw's own MCP tool-calling layer imposes a timeout shorter
  than 30s on *remote* MCP tool calls specifically (as opposed to the
  `process` tool's documented 30s cap, which is a different mechanism) was
  not separately confirmed in this pass — flagged as a gap, not assumed
  equal.

### Net effect on the source spec's section 18 open questions

1. **Grok Bot connector timeout vs. the 40s long-poll design: SAFE,
   confirmed with 4.5x headroom** (3 min vs. 40s). No redesign needed on
   the Grok Bot side.
2. **OpenClaw as a contestant/reference-bot runtime: the 40s design is NOT
   safe as a single blocking call** — confirmed 30s ceiling on the
   `process` poll mechanism. If any BOTTAGON reference bot, doctor tool, or
   OpenClaw-driven contestant is built, it needs the background-and-poll
   pattern, not a single 40-second blocking HTTP call. This is a real,
   concrete design input for whichever milestone builds the reference bot
   (source spec's `cmd/refbot`) and the OpenClaw skill file (section
   11.12) — worth deciding explicitly before that work starts, not
   discovering it as a bug later.
3. **MCP OAuth (source spec open question 18.1): resolved, no pull-forward
   needed.** Static bearer auth is confirmed working today for Grok's
   custom MCP connectors.
4. Hosting/domain (18.3/18.4) and moderation provider (18.2) — still
   genuinely open, not addressed in this pass, no urgency yet.
